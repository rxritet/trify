# Trify — план проекта

**Статус:** разработка frontend-прототипа и дизайна; backend и Firebase отложены по запросу пользователя.  
**Основа:** описание Trip Planner и предоставленное задание `individual_project_flutter_ru.docx`, тема 10.  
**Название приложения:** Trify.

Этот документ собирает исходную идею, объём первой версии и учебный план. Требования недель 1–8 сверены с оригинальным заданием, предоставленным 11 октября 2026 года. Пользователь выбрал сначала подготовку frontend, затем подключение backend и Firebase. Визуальное направление и границы текущего прототипа описаны в [design.md](design.md).

В родительском каталоге уже есть Flutter-проект. Папка `Trify` на текущем этапе содержит только документацию; структура кода ниже — ориентир для будущей разработки.

## 1. Идея и аудитория

Trify помогает путешественникам и туристам собрать поездку в одном приложении: выбрать направление и даты, найти интересные места, распределить посещения по дням, посмотреть маршрут на карте и сохранить заметки. Ранее сохранённая информация должна оставаться доступной без интернета; аккаунт обеспечивает хранение и синхронизацию поездок между устройствами.

Главный пользовательский сценарий:

1. Зарегистрироваться или войти.
2. Создать поездку, указав название, город и даты.
3. Найти места и добавить их в поездку.
4. Распределить места по дням, задать время и порядок посещения.
5. Добавить заметки и открыть маршрут на карте.
6. Сохранить план и открыть его позже, в том числе без интернета.

Пример: поездка в Астану на 10–12 ноября 2026 года с посещением Байтерека, Хан Шатыра, Национального музея, EXPO, Ботанического сада и большой мечети. Пользователь самостоятельно выбирает день и время для каждого места.

## 3. Экраны и навигация

В описании указан минимум из пяти экранов. Целевая структура Trify включает девять основных экранов/групп экранов:

| Экран | Назначение |
|---|---|
| Splash | Старт приложения и проверка сессии |
| Login / Register | Вход, регистрация, Google Sign-In |
| Home | Обзор поездок, ближайшие и прошедшие поездки, создание новой |
| Create / Edit Trip | Название, направление, даты, описание |
| Trip Details | План по дням; разделы Plan, Map и Notes |
| Explore / Places | Поиск, категории, избранное, добавление места |
| Place Details | Фото, описание, рейтинг, адрес; часы работы при наличии данных |
| Map | Маркеры, положение пользователя и маршрут выбранного дня |
| Profile / Settings | Аккаунт, тема, язык, уведомления, офлайн-данные, выход |

Нижняя навигация: **Home · Explore · Trips · Profile**. `Trips` — полный список поездок, `Home` — обзор и ближайшие планы; окончательное различие уточнить при проектировании интерфейса.

План маршрутов GoRouter, приведённый к единому формату:

- `/login`, `/register`;
- `/home`, `/explore`, `/trips`, `/profile`;
- `/trips/new`, `/trips/:tripId`, `/trips/:tripId/edit`;
- `/trips/:tripId/map`;
- `/places/:placeId`.

Предусмотреть именованные маршруты, параметры, вложенную навигацию и защиту разделов поездок и профиля по состоянию авторизации. Интерфейс — Material 3, системная/светлая/тёмная тема, поддержка телефона и планшета, портретной и альбомной ориентации.

## 4. Модель данных

| Сущность | Поля из исходного описания |
|---|---|
| `User` | `id`, `name`, `email`, `photoUrl`, `createdAt` |
| `Trip` | `id`, `userId`, `title`, `city`, `country`, `startDate`, `endDate`, `description`, `coverImage`, `latitude`, `longitude` |
| `Place` | `id`, `name`, `description`, `category`, `address`, `imageUrl`, `latitude`, `longitude`, `rating` |
| `TripPlace` | `id`, `tripId`, `placeId`, `day`, `visitTime`, `order`, `note` |

`TripPlace` связывает место с поездкой и хранит параметры конкретного посещения. Пример: Байтерек, день 1, 10:00, позиция 1, заметка «купить билет заранее».

При уточнении схемы определить необязательные поля, идентификаторы внешнего API, хранение избранного и фотографий поездки. Согласовать `day` и календарную дату посещения: в исходном тексте встречаются оба варианта. Проверять корректность диапазона дат, принадлежность дня поездке и порядок мест.

## 5. Архитектура и стек

Базовый подход — Clean Architecture с разделением по функциям. Поток вызовов: экран → Riverpod notifier/provider → use case → интерфейс repository → реализация repository → источник данных. Domain не должен зависеть от Flutter, Firebase или HTTP-клиента.

Предлагаемая структура относительно корня будущего приложения:

```text
lib/
  core/
    constants/
    errors/
    network/
    router/
    theme/
    utils/
  features/
    auth/
    trips/
      data/
        datasource/
        models/
        repositories/
      domain/
        entities/
        repositories/
        usecases/
      presentation/
        screens/
        widgets/
        providers/
    places/
    map/
    profile/
  firebase/
  services/
  main.dart
```

В остальных функциях применять аналогичное разделение на `data`, `domain` и `presentation` по мере необходимости. Сохранять архитектуру понятной для защиты, не создавать абстракции без практической задачи.

| Задача | Рекомендация из описания |
|---|---|
| Приложение и язык | Flutter, Dart |
| Управление состоянием | Provider на учебном этапе, Riverpod в основной архитектуре |
| REST и JSON | http, Wikimedia REST API; Freezed и json_serializable при усложнении моделей |
| Навигация | GoRouter |
| Авторизация и облачные данные | Firebase Auth, Cloud Firestore |
| Push-уведомления | Firebase Cloud Messaging |
| Локальная база и настройки | Hive, SharedPreferences |
| Карта и геолокация | Google Maps, geolocator |
| Кэш изображений | cached_network_image |
| Фото | camera или image_picker; выбрать при реализации |
| Dependency Injection | Riverpod; get_it только при обоснованной необходимости |
| Тестирование | flutter_test, mocktail, integration_test |
| CI/CD | GitHub Actions |
| Отчёты об ошибках | Firebase Crashlytics |

Это планируемый стек, без фиксации версий и установки пакетов. Совместимость и актуальность технологий проверить перед реализацией.

## 6. API, Firebase и офлайн-доступ

### Внешние данные

Для поиска мест выбран публичный Wikimedia REST API без ключа: `GET https://ru.wikipedia.org/w/rest.php/v1/search/page?q={query}&limit=20`. Он отдаёт заголовок, краткое описание и, когда доступно, миниатюру. Геоданные, отзывы, расписание и построение маршрутов этот этап не обещает; для них позже понадобится отдельный провайдер.

Для Explore предусмотреть JSON-модели, загрузку, успешный результат, пустой список и ошибку; поиск с debounce, pull-to-refresh и пагинацию при поддержке API. Данные карточки отображать с учётом того, какие поля действительно предоставляет сервис.

Отдельно выбрать источник построения маршрутов. Отображение Google Maps и расчёт пути между точками — отдельные интеграционные задачи; уточнить транспорт, лимиты запросов и условия использования данных.

### Пользовательские данные

- Firebase Authentication: email/пароль и Google Sign-In.
- Cloud Firestore: профиль, поездки и связанные посещения; доступ к личным данным только владельцу.
- В исходном описании предложены две схемы: коллекции `users`, `trips`, `tripPlaces` либо поездки внутри `users/{userId}/trips`. Выбрать одну схему до реализации repository и правил доступа.
- FCM: получение push-уведомлений, обработка открытия и настройки уведомлений. Сценарии — «поездка начинается завтра» и «сегодня запланировано несколько мест».
- Механизм планирования и отправки таких напоминаний пока не определён. Перед реализацией выбрать серверную отправку для FCM; при необходимости отдельно предусмотреть локальные напоминания.

### Локальные данные

Hive хранит поездки, места, избранное и кэш ответов API. SharedPreferences хранит настройки темы и языка.

Repository выдаёт сохранённые данные и обновляет их при наличии сети. Без сети ранее сохранённая поездка и заметки доступны из локального хранилища. Доступность фотографий зависит от выбранного кэша изображений.

До реализации согласовать, разрешено ли редактирование офлайн, как повторять отправку изменений и разрешать конфликты между устройствами. Офлайн-карты и расчёт новых маршрутов без сети в исходном описании не определены и не входят в обещанный объём первой версии.

## 7. Нативные функции

- Геолокация через geolocator: разрешения, текущая позиция, сценарии отказа и выключенной службы геолокации.
- Камера: сделать фото и добавить его в галерею поездки. Место хранения и необходимость облачной загрузки определить отдельно.
- Собственный Flutter MethodChannel → Android/Kotlin: получить заряд батареи, модель устройства и версию Android; показать сведения в настройках. Минимальный учебный сценарий — получение уровня заряда.

Android — приоритет для Kotlin Platform Channel, APK/AAB и подготовки публикации. Объём поддержки iOS требуется уточнить отдельно.

- [ ] Работают регистрация, вход по email и Google, выход и защита личных разделов.

- [ ] Ранее сохранённые поездки доступны без интернета; тема и язык сохраняются.

7. Проверить совместимость пакетов и определить конфигурацию Firebase, Maps и release-сборки.
