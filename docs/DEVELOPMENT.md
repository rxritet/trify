## Подтверждённое состояние приложения

- Реализован Flutter-интерфейс с графитовой и светлой темами, крупными фотографиями, экранами входа, главной, поиска мест, поездок и профиля. На узких экранах используется нижняя навигация, на широких — боковая.
- Локальные регистрация и вход: на Android через `sqflite` (`lib/features/auth/data/user_repository_io.dart`), в веб-версии через `shared_preferences` (`user_repository_web.dart`). Это прототип учётных записей, не готовая серверная авторизация. Демонстрационный пользователь создаётся кодом; перед публичным релизом пересмотреть этот механизм и хранение паролей.
- Firebase-проект подключён к веб-версии для Google-входа (`firebase_bootstrap.dart`, `firebase_options.dart`, `auth_controller.dart`). 18 октября 2026 года в существующем проекте зарегистрировано Android-приложение `com.student.tripplanner.trip_planner`, добавлен debug SHA-1, а актуальный `android/app/google-services.json` подключён к Gradle. Код использует нативный `google_sign_in`; debug APK собран после конфигурации. 19 октября 2026 года Google-вход успешно проверен на Android-эмуляторе: пользователь завершил системный вход, после чего Trify вернулся на передний план.
- Cloud Firestore Standard создан в существующем проекте в `asia-south2 (Delhi)`. `CloudPlannerStore` хранит поездки, заметки и избранное Google-пользователя в приватном пути `users/{Firebase UID}/planner/state`, оставляя локальную копию офлайн-резервом. Правила Firestore запрещают весь доступ по умолчанию и разрешают путь только совпадающему Firebase UID. 19 октября 2026 года запись снимка успешно проверена на Android-эмуляторе после изменения избранного. Локальные email/password-аккаунты пока остаются локальными; для них не создаются Firebase Auth-пользователи автоматически.
- Поиск мест обращается к русской Википедии через `WikimediaPlacesRepository`; `PlacesRepository` и `PlacesController` отделяют источник данных от интерфейса. Остальные демонстрационные места находятся в `demo_data.dart`.
- `PlannerState` сохраняет поездки, места в плане, заметки и избранное в локальном хранилище через `PlannerRepository`. Состояние изолировано по идентификатору пользователя; прежний общий ключ не переносится автоматически, потому что у него нет владельца. При Google-входе данные дополнительно синхронизируются через Firestore. При первом запуске отображаются демонстрационные поездки; после изменений состояние восстанавливается после перезапуска. Тема пока не сохраняется между запусками.
- Текущее состояние управляется `ChangeNotifier`, `InheritedNotifier` и локальным `setState`; Riverpod, GoRouter, карты, уведомления, CI/CD и готовый release-пакет остаются планами, а не реализованными возможностями.

## Как развивать приложение

- Сохранять работающие сценарии `Explore → карточка места → поездка → план по дням` и существующие визуальные решения. Добавлять хранилище и облачные интеграции через репозитории, не выполнять запросы API или обращения к базе прямо в виджетах.
- Для сетевых экранов предусматривать загрузку, данные, пустой результат и ошибку. Для постоянного хранения поездок определить модель данных, миграции и поведение без сети; проверять, что обновление приложения сохраняет пользовательские данные.
- Для Android Firebase приложение, debug SHA-1 и `google-services.json` уже настроены; Google-вход проверен в debug-сборке на Android-эмуляторе. Для release-версии добавить SHA-1 release/upload-ключа и отдельно проверить вход с release-подписью.
- Перед публичным выпуском заменить или переработать прототип локальной авторизации, убрать демонстрационные учётные данные из релизного сценария и проверить правила доступа к будущим облачным данным.
- Не расширять первую версию бронированиями, платежами, AI-планированием или социальными функциями без запроса пользователя. Офлайн-доступ означает работу с ранее сохранёнными данными; офлайн-карты и построение маршрутов требуют отдельного решения.

## Выпуск и последующие обновления

- Сейчас в `pubspec.yaml` указано `1.0.0+1`. Android release-сборка использует upload-ключ из локального `android/key.properties`, если он настроен; до этого сборка намеренно получает debug-подпись только для технической проверки. Шаблон находится в `android/key.properties.example`.
- Android launcher-иконки во всех текущих `mipmap-*` плотностях собраны из `assets/branding/trify-avatar-concept-04.png`; обновлённая debug-сборка установлена на эмулятор. Для Google-входа новая иконка попадёт в следующую установку приложения, но экран выбора аккаунта не открывался повторно только ради визуальной проверки.
- На этом компьютере `flutter doctor` сообщает об отсутствии Android `cmdline-tools` и неподтверждённых лицензиях. Из-за этого Flutter не может выполнить финальную проверку AAB через `apkanalyzer`, хотя Gradle создаёт bundle. Перед публикацией установить `Android SDK Command-line Tools (latest)`, принять лицензии и повторно проверить `flutter doctor`.
- 17 октября 2026 года `dart analyze lib test` и все 19 Flutter-тестов прошли. Свежий debug APK собран; release AAB создан как технический артефакт, но до создания upload-ключа он имеет debug-подпись и не предназначен для Play Console.
- До первой публикации утвердить постоянный `applicationId`, настроить безопасное хранение upload-ключа, release-подпись, иконку, название приложения, политику конфиденциальности и материалы магазина. Не помещать приватные ключи, пароли и файлы подписи в проект.
- Для каждого релиза проверить основной сценарий на Android, увеличить номер сборки после `+` в `pubspec.yaml`, собрать подписанный AAB и выпустить его сначала в тестовом канале. APK можно собирать для прямой установки и тестирования; публикация через Google Play предполагает цикл выпуска новых сборок. Изменение исходного кода само по себе не обновляет установленное приложение.
- Для совместимости обновлений сохранять `applicationId` и преемственность подписи, планировать миграции локальных данных. Проверять требования Google Play непосредственно перед публикацией: они меняются.
- По завершении изменений запускать соразмерные проверки: форматирование и анализ для кода, релевантные тесты, ручную проверку затронутого сценария. Не объявлять APK, Android-вход или полный набор тестов проверенными без фактического результата. Для правок документации достаточно сверить текст, пути и ссылки.
